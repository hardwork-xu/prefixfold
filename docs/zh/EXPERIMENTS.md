## 冻结目标与实测判断

[targets.json](../../research/targets.json) 与 [benchmark.json](../../configs/benchmark.json) 在调优前固定目标：float32，`B=16,H=4,P=4096,S=128,D=64`，5 次预热，每种实现 30 次实测，块宽 1,024，显式临时空间预算 8 MiB。每个请求、每个头只有一个查询。

| 指标 | 主实验前固定的 Target | 主工作负载的 Measured | 判断 |
|---|---:|---:|---|
| 相对复制前缀的稠密 KV，自有 K/V 数组载荷减少 | 至少 80% | 90.9091%，132 MiB 降至 12 MiB | 达标 |
| SDPA 中位数 / PrefixFold 中位数 | 至少 1.25 倍 | 3.5036 倍，7.1603 ms / 2.0437 ms | 达标 |
| 全部工作负载/实现正确性检查 | 相对 float64，`atol=3e-5, rtol=3e-5` | 28/28 通过 | 达标 |

**Expected/Theoretical（预期/理论）：** 公共前缀只存一份，使该部分载荷减少到原来的 `1/B`；算术复杂度不变。**Measured（实测）：** 被计时实现实际使用的 K/V 数组占用上表中的字节数。两者均不能证明进程内存也减少相同比例。基准的 K/V 载荷不含 int64 长度数组，而公开 `DecodeBatch.kv_nbytes` 属性包含它。

## 环境与来源记录

主实验使用 Apple M1 Pro、10 个逻辑 CPU、16 GiB 物理内存、Darwin 25.6.0 arm64、Python 3.12.2、NumPy 2.2.6、PyTorch 2.8.0、PrefixFold 0.1.0。已安装两库的构建配置均标识 Apple Accelerate BLAS。记录的 PyTorch 算子内线程数与可见 OpenMP 线程池均为 1；`OMP_NUM_THREADS`、`OPENBLAS_NUM_THREADS`、`MKL_NUM_THREADS`、`VECLIB_MAXIMUM_THREADS`、`NUMEXPR_NUM_THREADS` 均请求 1。`threadpoolctl` 无法观察 Accelerate 是否遵守设置。因此这是 **请求单线程的 CPU 结果**，不能证明所有 BLAS 内部操作都只使用一个操作系统线程。

主实验 `20260921T121914Z-56a3bc9a` 于 `2026-09-21T12:19:14.085647+00:00` 开始，`2026-09-21T12:19:45.075223+00:00` 完成。测试的 Git revision 为 `70e7ed50e51b4de74a9d35c358068aa689a939c5`，相关源码干净。源码清单 SHA-256 为 `c0003d3eaf2887a4b8a026e9139ea2cc783d76487fa219f9bdaeac15c9b7d500`；原始记录还包含逐文件哈希与配置哈希，即使之后增加文档提交，也能定位被测实现。


源码 `99e2958` 的原始主实验与三次分块实验完整保留在 [results/pre-resource-fix](../../results/pre-resource-fix)，包含全部 1,200 个测量。资源审查发现，小维度下原临时空间估计未保守覆盖整数索引/掩码临时数组，因此最终源码将估计从 `4B(3T+8D+32)` 修改为 `4B(4T+8D+32)`。原始目标、工作负载配置、种子与实际有效块宽均未改变。随后重跑完整主实验和三次分块实验，得到本页引用的 1,200 个最终测量。不能把两个会话的耗时差异解释成这次数值资源估计修复带来的优化收益。

全部 Q/K/V 均为 **固定种子的 float32 正态分布合成数据**，不包含预训练模型、私有数据集或生产请求轨迹。基础种子为 `20260921`，各工作负载加上索引，主场景实际种子为 `20260925`。同一场景的四个实现使用相同输入种子和形状，不等长后缀长度也显式保存。

## 基线与计时协议

| 实现 | 实际计算及用途 |
|---|---|
| `torch_sdpa` | CPU `torch.nn.functional.scaled_dot_product_attention`，连续稠密 KV、布尔有效掩码、dropout 为零；实用库基线 |
| `numpy_dense` | 批量 NumPy 矩阵乘法、稳定 softmax、相同掩码与 float32 算术；与 PrefixFold 使用同一数组库的第二个实用基线 |
| `prefixfold` | 共享前缀查询分组、分块在线归约、私有后缀批处理、带验证的公开 API |
| `ungrouped` | 相同前缀所有权、计划与后缀代码，仅改为逐请求计算前缀查询 |

float64 `dense_reference` 是正确性参考，不参与性能竞争。PyTorch 自行选择 CPU 实现，本实验没有运行 CUDA FlashAttention。即使两库都使用 Accelerate，库派发、融合、向量化与 Python 开销仍有差异。PrefixFold 计时包含公开接口的查询验证、计划选择和批次锁；稠密基线闭包的输入已提前生成/验证。因此对比不等于隔离机器指令，也不假设实现开销完全相同。

每个场景为每种实现创建独立、常驻工作进程，各进程导入同样的库，包括 NumPy 与 PyTorch。父进程每次只要求一个工作进程计算，其他进程空闲。初始工作进程顺序及每轮预热/实测顺序均按种子打乱。工作进程使用 `perf_counter_ns` 对同步 CPU 计算计时，不包含进程通信与派发请求。保留全部有效观测：主实验共 **7 个场景 × 4 种实现 × 30 次 = 840 个实测样本**，另有 140 次预热和 28 次首次调用。这是一台机器的一次实验会话，不是 840 次独立硬件试验。

输入生成、缓存构建/加载、稠密 KV 物化与张量视图准备分别计时。首次调用指准备后的首次计算，不含 Python 进程启动与导入。正确性比较和预热位于稳态测量之前。计算路径包括输出分配，以及该实现存在的 NumPy/PyTorch 返回转换。计时范围没有模型加载、预处理、设备传输、Token 生成或完整应用请求。**这是算子计时，不是端到端生成延迟。**

基准拒绝单对稠密 KV 超过 1 GiB 的配置。工作进程设置响应超时；错误与超时保存状态和错误文本，不会转成零延迟。主实验 28 条实现记录全部通过，每条有 30 个样本，工作进程均成功退出。主实验没有失败、超时或跳过场景。

## 全部主实验工作负载

所有行均使用 `H=4,D=64`，耗时为毫秒中位数。`S*` 表示不等长后缀预留容量，不代表实际长度都相同。

| 场景 `(B,P,S)` | NumPy ms | SDPA ms | PrefixFold ms | 不分组 ms | SDPA / PrefixFold | KV 减少 |
|---|---:|---:|---:|---:|---:|---:|
| `no_prefix` `(16,0,128)` | 0.2029 | 0.2480 | 0.4081 | 0.4193 | 0.608× | 0.00% |
| `single_request` `(1,4096,128)` | 0.4663 | 0.5357 | 0.8819 | 0.8724 | 0.607× | 0.00% |
| `short_prefix` `(16,128,128)` | 0.4352 | 0.4766 | 0.5631 | 1.3192 | 0.846× | 46.88% |
| `shared_b4_p4096` `(4,4096,128)` | 1.6612 | 1.8942 | 1.0748 | 2.0978 | 1.762× | 72.73% |
| `shared_b16_p4096` `(16,4096,128)` | 6.6804 | 7.1603 | 2.0437 | 7.2138 | 3.504× | 90.91% |
| `shared_b32_p8192` `(32,8192,128)` | 26.2760 | 28.0105 | 4.8808 | 27.1801 | 5.739× | 95.38% |
| `ragged_suffix` `(16,4096,256*)` | 6.7725 | 7.1991 | 2.5668 | 7.1642 | 2.805× | 88.21% |

不等长场景为每个请求预留 256 个后缀位置，实际长度为 `[29,80,230,231,225,205,46,39,203,248,179,136,234,184,202,98]`。稠密基线物化到最长有效长度 248，而 PrefixFold 保留完整容量；报告的载荷减少比例已经计入这一差异。

[完整 28 行表格](../../results/table_zh.md)、[summary.json](../../results/summary.json) 与[延迟图](../../results/latency.svg) 由 [scripts/analyze.py](../../scripts/analyze.py) 从原始测量生成。图使用对数延迟轴。吞吐字段统计查询向量（`B*H / 秒`），不是生成 Token。

固定主场景中，分组让不分组中位数从 7.2138 降到 2.0437 ms，比值为 3.5298 倍，存储的 KV 与后缀计算相同。相对 NumPy 稠密实现为 3.2688 倍。这支持前缀查询分组是当前工作负载中的有效机制，但不能证明数据流量也下降相同倍数，因为没有使用硬件计数器测量内存流量。

不利场景同样重要：无前缀时只有 SDPA 的 0.608 倍速度，单请求为 0.607 倍，短前缀为 0.846 倍。前两者没有存储节省；短前缀即使减少 46.875% 载荷，也未获得更快注意力。Python 派发、临时数组与归约工作可能主导耗时。`P=0` 或 `B=1` 时，两种分组模式的算术路径等价；观测到的耗时差异属于噪声及进程/运行时因素，不能解释为分组优化收益。

## 准备、首次调用、内存与波动

下表来自主工作负载，各项计时范围不同，不能简单相加中位数后宣称测得完整请求。

| 实现 | 共用输入构建 ms | 实现准备 ms | 首次计算 ms | 稳态中位数 ms | 整个工作进程峰值 RSS MiB |
|---|---:|---:|---:|---:|---:|
| `prefixfold` | 17.8804 | 0.0772 | 2.7534 | 2.0437 | 243.031 |
| `ungrouped` | 16.2873 | 0.0164 | 7.7288 | 7.2138 | 223.656 |
| `torch_sdpa` | 15.3498 | 13.6900 | 9.5335 | 7.1603 | 370.844 |
| `numpy_dense` | 14.8978 | 12.2113 | 9.9379 | 6.6804 | 380.812 |

`peak_worker_rss_bytes` 是操作系统记录的进程内存高水位，覆盖导入、输入、基线物化、float64 正确性计算和计时调用。基线在稳态计时前释放共享源，但此前的分配仍影响峰值 RSS。RSS 不是注意力临时空间、增量分配测量，也不是同时驻留工作进程的内存总和。90.9091% 的结论只使用 K/V 数组有效载荷。`AttentionPlan` 的 8 MiB 预算不包含输入/输出与厂商工作空间，也不是进程硬限制。

主场景 PrefixFold 样本范围为 1.4868–2.4598 ms，样本标准差 0.3023 ms；SDPA 范围为 6.9532–7.4807 ms，标准差 0.1406 ms。不等长场景的 PrefixFold 范围为 1.8255–3.3839 ms；最大规模场景中，PrefixFold 和 SDPA 分别包含 13.7206 ms 和 72.2465 ms 的观测。全部保留这些样本。每种实现 30 个观测不足以支持 p99 或强尾延迟结论。本项目不声称置信区间、热状态稳定、CPU 绑核或受控多会话可重复性已经验证。

全部主实验 PrefixFold 场景均满足声明的混合绝对/相对容差；跨场景最大绝对误差为 `2.0915591120163057e-7`，主场景为 `1.0125361699087065e-7`。参考输出接近零时，原始最大相对误差可能超过 `3e-5`；验收规则是 `abs(actual-reference) <= atol + rtol*abs(reference)`，不是单独相对误差上界。

## 主实验后的分块敏感性

保留固定主实验后，又对主场景形状测试块宽 256、1,024 和 4,096。三次额外运行均使用种子 `20260921`，彼此输入相同，但不同于主实验的主场景输入。它们使用相同被测源码哈希、四种实现、5 次预热和每实现 30 个样本，共增加 360 个实测样本。所有实现均通过正确性检查。这是探索性敏感性实验，不替代冻结的 1,024 Token 主结果。

| 块宽 | PrefixFold 中位数 ms | 不分组中位数 ms | SDPA 中位数 ms | NumPy 中位数 ms | 原始记录 |
|---:|---:|---:|---:|---:|---|
| 256 | 2.7249 | 15.9835 | 7.2366 | 6.8120 | [tile256.json](../../results/tile256.json) |
| 1,024 | 2.3479 | 7.2505 | 7.1777 | 6.6577 | [tile1024.json](../../results/tile1024.json) |
| 4,096 | 1.9245 | 4.2925 | 7.1430 | 6.5834 | [tile4096.json](../../results/tile4096.json) |

较大块在此更快，特别是不分组循环，符合摊薄派发/归约开销的解释，但也使用更多分数工作空间。运行的块宽顺序是 256、1,024、4,096，块宽顺序未随机化，每次运行内部的实现顺序仍随机化。独立会话、可能的运行时漂移与单一形状不能确定最优分块规则；默认值和原始目标均未修改。配置见 [tile256.json](../../configs/tile256.json)、[tile1024.json](../../configs/tile1024.json) 和 [tile4096.json](../../configs/tile4096.json)。

## 复现与结论范围

```sh
make install
.venv/bin/python benchmark.py --config configs/benchmark.json --output results/reproduced.json
.venv/bin/python scripts/analyze.py --input results/reproduced.json --output-dir results/reproduced-analysis
.venv/bin/python benchmark.py --config configs/tile256.json --output results/reproduced-tile256.json
.venv/bin/python benchmark.py --config configs/tile1024.json --output results/reproduced-tile1024.json
.venv/bin/python benchmark.py --config configs/tile4096.json --output results/reproduced-tile4096.json
```

主实验记录的命令为 `python benchmark.py --config configs/benchmark.json --output results/benchmark.json --variants prefixfold ungrouped torch_sdpa numpy_dense --timeout 120`。上方命令使用新结果路径以保留入库证据。`scripts/analyze.py` 默认只写分析产物；仅显式传入 `--update-readme` 时才更新 README 基准区段，因此只有选定的发布主实验应使用该参数。

证据支持当前实现对这些合成 CPU 形状有效，尤其是多请求、长共享前缀。它不证明服务吞吐、模型输出质量、GPU/MPS 加速、Linux 容器性能或对所有 CPU 的优势。填充溢出问题在被测 revision 前已修复，并有回归测试；有效分数超出 float32 范围时仍会按设计拒绝。接下来有价值的实验包括独立会话重复、通过明确模型集成获得有代表性的投影 KV 轨迹，以及在未用于选规则的形状上验证实现选择策略。
